# 017 — Catalogue contract: UUID course ids, price in pence, selection in the URL

**Status:** accepted · **Date:** 2026-10-02

## Context
Slice 1 exposes courses to the SPA, and slice 2 will reference a course from an order
seat. Three things have to be fixed before either side is written: how a course is
identified, how its price is represented, and how the parent's choice of course and year
reaches the checkout.

## Decision

| Aspect | Choice |
|---|---|
| Course identity | UUID primary key generated by the database. `subject` is unique and is the key the seed upserts on |
| Price | Integer pence: `pricePence` in the table and in the contract. The SPA formats it as pounds |
| Endpoint | `GET /api/courses` returns a plain array of courses, ordered by subject |
| Hand-off to checkout | The product page ends with "Continue to checkout", which opens `/checkout?courseId=<id>&year=<n>` |

The year is chosen on the product page, from the selected course's range. The server
validates the year against the range when the order is created (slice 2).

## Alternatives considered
- A readable slug as the primary key — stable and pleasant in URLs, but a natural key is
  awkward once a subject is renamed or split per year.
- `Decimal` for the price — reads like money in SQL, but arrives in JSON as a string.
- Router state or client storage for the selection — a clean URL, but the choice is lost
  on reload or when the link is opened directly.

## Consequences
- Money never passes through floating point.
- The checkout URL survives a reload and can be opened directly; its values are editable
  by the user, so the server never trusts them.
- Course ids differ between databases; tests and the seed address courses by subject.

## In production
Prices would carry a currency and come from a pricing service; course pages would have
readable URLs.
